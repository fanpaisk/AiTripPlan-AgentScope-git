# EXP-001 报告：单 Agent vs 多 Agent 对照实验

> 设计见 `design.md`，两臂提示词见 `prompts.md`，原始数据见 `raw/`、`results.csv`、`score.csv`。
> 全部 token 数字均来自 `experiment-run.ps1 -Recollect` 的**事后重采权威值**（原因见 `design.md` §3.1）。

日期：2026-10-05
样本：**3 个 prompt × 2 臂 × n=2 = 12 次运行**（全部 `status=SUCCESS`）

---

## 摘要（三条结论）

1. **质量打平。** 盲评总分 21.33 vs 21.17（满分 25，差 0.8%）；6 对里 3 平、多 Agent 胜 2、单 Agent 胜 1。**多 Agent 的分工没有带来可测量的质量收益。**
2. **单 Agent 贵 2.2 倍，而且方差灾难性更大。** 均值 569,371 vs 258,435 token；单 Agent 区间 **92,390 ~ 1,924,552（21 倍）**，多 Agent 155,181 ~ 416,544（2.7 倍）。
3. **单 Agent 更快**（均值 44s vs 57s，快 23%）。

> **一句话**：在这套实现里，多 Agent 买到的是「更便宜 + 更稳定 + 更如实」，代价是「慢 23%」；而它**没有买到更好的方案质量**。

---

## 1. 结果明细

### 1.1 token（权威值）

| prompt | rep | multi | single | single/multi |
|---|---|---|---|---|
| P1 深圳→惠州 3 日游 | r1 | 401,962 | 642,015 | 1.60× |
| P1 | r2 | 416,544 | **1,924,552** | **4.62×** |
| P3 杭州亲子 3 天 | r1 | 196,381 | 181,549 | 0.92× |
| P3 | r2 | 155,181 | 187,767 | 1.21× |
| P4 深圳一日游 | r1 | 206,454 | 387,951 | 1.88× |
| P4 | r2 | 174,088 | 92,390 | 0.53× |

| 臂 | n | 合计 | 均值 | 区间 |
|---|---|---|---|---|
| multi | 6 | 1,550,610 | **258,435** | 155,181 ~ 416,544（2.7×） |
| single | 6 | 3,416,224 | **569,371** | 92,390 ~ 1,924,552（**21×**） |

**按 prompt 聚合**（同一题两臂各 2 次）：

| prompt | multi 均值 | single 均值 | 比值 |
|---|---|---|---|
| **P1**（多城路线 + 行程） | 409,253 | 1,283,284 | **3.14×** |
| **P3**（行程 / 预算为主） | 175,781 | 184,658 | **1.05×（打平）** |
| **P4**（简单一日游） | 190,271 | 240,170 | 1.26× |

> **关键洞察：单 Agent 的劣势几乎全部来自「需要大量地图查询」的题。**
> P1 涉及多段城市间算路（罗浮山 / 西湖 / 巽寮湾 / 双月湾），单 Agent 把每一次地图返回结果都留在上下文里并反复重发；P3 以行程与预算为主、地图查询少，两臂就基本打平。
> **也就是说：不是"单 Agent 一定更贵"，而是"单 Agent 对长上下文工具结果不耐受"。**

### 1.2 延迟

| 臂 | 均值 | 逐轮 |
|---|---|---|
| multi | **57s** | 50 / 56 / 69 / 74 / 48 / 47 |
| single | **44s** | 37 / 70 / 37 / 48 / 39 / 34 |

单 Agent 在 6 对里快 5 对。省掉的是 A2A 往返与子 Agent 的启动/初始化开销。

### 1.3 质量（盲评，5 维 × 1-5 分，3 次取中位数）

| 臂 | **总分(/25)** | facts 事实可用 | cover 覆盖度 | action 可执行 | struct 结构 | honest 如实性 |
|---|---|---|---|---|---|---|
| multi | **21.33** | 3.83 | 5.00 | 3.33 | 4.83 | **4.33** |
| single | **21.17** | 3.83 | 5.00 | **4.17** | 4.83 | 3.33 |

逐题胜负：`P1r1 平` / `P1r2 平` / `P3r1 平` / `P3r2 multi` / `P4r1 multi` / `P4r2 single`
→ **3 平 2 胜 1 负**，无一方占优。

**两处值得单说**：

- **`honest`（如实性）多 Agent 明显更好（4.33 vs 3.33）**：多 Agent 更倾向于标注「该数据为估算」；单 Agent 更容易把估算当真实数据写。
  这与已知缺陷 **D2**（Agent 会编造失败原因）呼应 —— 提示**如实性上多 Agent 的二次汇总起了「复核」作用**。
- **`action`（可执行性）单 Agent 更好（4.17 vs 3.33）**：单 Agent 方案内部更自洽；多 Agent 因为要缝合两份子报告，偶发「路线表与每日行程对不上」这类矛盾（评审原话：*「路线表(含罗浮山)与每日行程(未游罗浮山)及预算门票存在自相矛盾」*）。

回答长度：multi 均值 3,039 字，single 3,138 字 —— **长度也基本一致**，说明不是"谁写得多谁得分高"。

## 2. 根因：钱花在上下文上，不是花在生成上

以最贵的 `single P1 r2`（1,924,552 token）为例：

| 项 | 值 |
|---|---|
| 观测数 | 52（`GENERATION 10` / `TOOL 31` / `SPAN 10` / `AGENT 1`） |
| token 分布 | **全部落在 GENERATION 上**；输入 1,910,571 / 输出 13,981 |
| **平均每次 LLM 调用输入** | **约 191,000 token** |
| 该轮 trace 数 | **1**（只有单 Agent 自己，无子 Agent 混入 —— 已排除窗口污染） |

单 Agent 一次持有 **10 个百度地图工具 + Skills + 计算 + 计划工具**，工具 schema 本身就是数万 token；再叠加 31 次工具返回（算路、POI、天气……）全量留在历史里，**每次调用都要重发一遍**。

对比 multi 的 `P1 r2`：4 个 trace（主管 + 子 Agent）、16 次 GENERATION、416,544 token —— 主管只把**子 Agent 的结论**（已被 `remote-result-max-chars: 8000` 截断）带进上下文，**天然的上下文隔离**。

> **一句话根因**：多 Agent 的真正价值不在"分工"，而在**上下文隔离** —— 每种子任务的重上下文只活在对应子 Agent 的进程里，主管只拿结论。

---

## 3. 可操作结论

1. **不要为了省钱去合并 Agent。** 在这个实现里合并反而贵 2.2 倍，且方差失控。
2. **单 Agent 要能用，必须先治上下文**：① 裁工具 schema（只为当前题挂必要工具）；② 工具结果落盘/摘要，不原样留在历史；③ 对历史做滑动窗口或压缩。做完之后值得再跑一次本实验对比。
3. **多 Agent 的短板是缝合**：`action` 分低源于两段报告拼接时的自相矛盾。可在主管的汇总提示词里加一条「交叉核对：路线表与每日行程必须一致」。
4. **简单任务（P4）也别急着上单 Agent**：1.26×，仍不划算。

## 4. 局限性（必须在引用本结论前读完）

| # | 局限 | 影响 |
|---|---|---|
| L1 | **n=2（每格只有 2 次重复）** | 只能看方向与离散度，**不做任何显著性宣称**。单 Agent 的 21 倍区间本身就说明方差巨大，n=2 的均值不稳定 |
| L2 | **评审模型与被评 Agent 是同一个模型**（DeepSeek） | 存在自我偏好风险；已用盲化 + 3 次取中位数缓解，但无法消除 |
| L3 | 只测了 3 个 prompt（省版），砍掉了 P2（强地图）、P5（欠约束） | 地图依赖最重的 P2 缺席；不过这恰好是 P1 已经覆盖的方向 |
| L4 | **A2 的输出契约做过一次修订**（见 `prompts.md` 第三节），且只改了 A2、没同步改 A1 | 已披露：A1 的提示词本来就有等价契约且实测合规。若要绝对对称，需两臂同改并重跑（约 104 万 token/对） |
| L5 | token 归属用**时间窗口**法（A2A 不传 trace 上下文） | 已做条数交叉校验与事后重采；仍不如 `session.id` 精确（见 `design.md` §3.1 的可选增强） |
| L6 | 全程依赖百度地图 MCP 在线 | 每轮运行前有门禁探活；但 D1 的地址失效是随机事件，本轮 12 次均正常 |
| L7 | 两臂迭代上限不对等（25 vs 40），方向对 A2 保守 | 已核对无一轮触顶（步数最高 88，`max-iters` 未达） |

## 6. 复现步骤

```powershell
# 1) 构建并启动（改了 .env 必须重打；先停再打包，否则 jar 被 JVM 锁住）
.\stop-all.ps1
mvn -B -s build-settings.xml clean package -DskipTests
.\run-all.ps1 -SkipBuild

# 2) 跑批（断点续跑：已存在的轮次自动跳过）
.\tools\experiment-run.ps1 -Arm multi,single -Prompts P1,P3,P4 -Reps 2

# 3) ★ 沉淀后重采（权威 token 值只认这一步的结果）
.\tools\experiment-run.ps1 -Recollect

# 4) 盲评
.\tools\experiment-judge.ps1
```

> ⚠️ 跑批期间**不要重启服务**（会打断窗口归属），也**不要在运行刚结束就读 token**（摄取延迟会造成 2 倍以上低估，见 `design.md` §3.1）。
