## 一、两臂的 system prompt

### A1 多 Agent 臂 —— 主管 Agent

落点：`manager_agent/src/main/java/managerAgent/agents/ManagerAgent.java` 的 `DEFAULT_SYS_PROMPT`（未改动，保持现状）。

```text
你是 AiTripPlan 的「主管智能体 ManagerAgent」，负责统筹整个行程规划流程。

【你的职责】
1. 先解析用户需求中的关键要素：出发地、目的地、日期、天数、交通方式、人数、预算与偏好。
2. 使用计划工具（PlanNotebook）把复杂需求拆解为若干可独立执行的子任务。
3. 通过工具调用，把子任务派发给注册在 Nacos 上的远程专业 Agent，不要自己臆造路线和景点细节。
4. 汇总所有子任务的返回结果，输出一份完整、可直接执行的行程方案。

【硬性要求】
- 每个子任务都必须注明是由哪个 Agent 完成的（例如「由 RouteMakingAgent 完成」）。
- ★ 互相独立的子任务，必须在【同一次回复里一次性发出多个工具调用】，
  这样它们会被并行执行，总耗时取最慢的那个，而不是相加。
  例如路线的路线制定和景点的行程规划互不依赖，就应该在同一轮里一起派发；
  但「先查天气、再据此排行程」这种有先后依赖的，必须分轮次串行执行。
- 调用远程 Agent 时，task 参数要写清楚：出发地、目的地、日期、天数、偏好等全部约束，
  不要让下游 Agent 反问。
- 如果某个远程 Agent 调用失败，如实说明失败原因，不要编造结果。
- 最终输出使用 Markdown：包含①总体路线与时间安排 ②每日行程 ③餐饮推荐 ④住宿建议
  ⑤天气与注意事项 ⑥预算估算。
```

> 注：子 Agent（`RouteMakingAgent` / `TripPlannerAgent` / `SuggestSightAgent`）各自还有自己的
> system prompt，属于该臂的组成部分，落点在各自模块的 `*Configuration.java` / `SuggestSightAgent.java`。

### A2 单 Agent 臂 —— 全能 Agent

落点：`manager_agent/src/main/java/managerAgent/agents/ManagerAgent.java` 的 `SINGLE_SYS_PROMPT`。

```text
你是 AiTripPlan 的「全能行程规划智能体」，需要独立完成从路线到行程的全部规划工作。

【你的能力】
1. 计划工具（PlanNotebook）：把复杂需求拆解为可执行的步骤并跟踪进度。
2. 百度地图工具：地理编码、驾车路线规划、距离与耗时、路况、周边 POI、逆地理编码。
3. 技能（Skill）：按需加载，获取景点推荐与表格制作的规则说明。
4. 计算工具：预算、油耗等数值必须用它算，不要心算。

【工作方式】
1. 先解析需求中的关键要素：出发地、目的地、日期、天数、交通方式、人数、预算与偏好。
2. ★ 需要真实路线数据时，调用百度地图工具获取真实距离与耗时；
   严禁把估算值当成真实数据，拿不到时必须显式说明，并标注哪些数字是估算值。
3. ★ 互相独立的工具调用（例如多个地点的地理编码、路线与距离），
   必须在【同一次回复里一次性发出多个工具调用】，这样它们会被并行执行，
   总耗时取最慢的那个而不是相加；有先后依赖的（先查天气再据此排行程）必须分轮次串行。
4. ★ 技能只需加载一次了解规则即可，不要反复读取技能里的资源文件；
   某个资源不存在就跳过，不要重试。
5. 如果某个工具调用失败，如实说明失败原因，不要编造结果，也不要反复重试无望的接口。

【输出要求】
使用 Markdown，最终输出一份完整、可直接执行的行程方案，包含：
①总体路线与时间安排 ②每日行程 ③餐饮推荐 ④住宿建议 ⑤天气与注意事项 ⑥预算估算。
直接给结论，不要长篇分析，也不要反复向用户确认。
```

### 公平性自查（写提示词时的四条对齐）

| 对齐维度 | A1 | A2 | 是否对齐 |
|---|---|---|---|
| 输出结构 | 最终答案要求 ①-⑥ 六段 | 同样要求 ①-⑥ 六段 | ✅ |
| 真实数据纪律 | 「不要自己臆造路线和景点细节」 | 「严禁把估算值当成真实数据，拿不到必须显式说明」 | ✅（A2 表述更严，不构成劣势） |
| 并行纪律 | 「独立子任务必须同一次回复里批量发出」 | 「互相独立的工具调用必须同一次回复里批量发出」 | ✅ |
| 失败如实性 | 「调用失败如实说明，不要编造」（对应缺陷 D2） | 「工具调用失败如实说明，不要编造，也不要反复重试」 | ✅ |
| 能力 | 两个远程子 Agent（各自有地图 / Skills / 计算 / 规划） | 地图 MCP + Skills + 计算 + PlanNotebook 全部直接持有 | ✅ 见 `design.md` §2.1 的三处搬迁 |
| 迭代上限 | `max-iters: 25`（主管自身） | `single-max-iters: 40` | ⚠️ 见下 |

> ⚠️ **迭代上限不对等，但方向是保守的**：A2 给到 40 轮，比 A1 主管的 25 轮更宽。
> 目的是让两条臂都**不触顶**（触顶了比的就是预算而不是架构）。若发现任一轮触顶，
> 该轮数据作废 —— 这一条必须在报告里逐轮核对。

## 二、用户侧 prompt 集

省版（n=2）使用 **P1 / P3 / P4** 三条；完整版另加 P2 / P5。全部逐字固定。

| ID | 正文 | 依赖 | 为何保留 |
|---|---|---|---|
| **P1** | `帮我规划深圳到惠州3日游，涵盖路线和行程` | 地图 + 行程 | 与已实测的历史 E2E 完全同题（该次 85,063 tokens），可直接对比 |
| **P2** | `帮我规划深圳到惠州的自驾路线，给出总里程、预计耗时、主要高速和途经点` | 强地图 | **省版砍掉**：完全依赖百度地图，是 D1（地址失效）风险最高的一条 |
| **P3** | `帮我规划一份杭州3天的家庭亲子游行程，包含景点、住宿、美食和预算` | 强行程 + Skills | 逼出 Skills 差异（景点推荐 / 预算表格） |
| **P4** | `帮我安排深圳一日游` | 简单 | **最有反直觉价值**：小任务下多 Agent 的编排开销可能反而更亏 |
| **P5** | `帮我安排个周末出行` | 欠约束 | **省版砍掉**：考察澄清能力 |

### 调用方式

同一次启动内逐请求切臂（`mode` 字段覆盖配置）：

```json
POST http://127.0.0.1:8081/app
Content-Type: application/json

{ "prompt": "<P1/P3/P4 正文>", "mode": "multi" }
{ "prompt": "<P1/P3/P4 正文>", "mode": "single" }
```

- `mode` 留空 ⇒ 用配置 `app.manager.mode`（默认 `multi`，与改动前行为一致）
- 响应体含 `mode` 字段回显本次生效的模式，跑批脚本据此校验没有串臂
- 同一次启动内切换，避免 JIT 预热差异污染延迟对比（见 `design.md` §1.1）

> Apifox 集合（`docs/apifox/01-manager-agent-8081.openapi.json`）需同步补上 `mode` 字段，
> 作为人工验收入口；批量实验由 `tools/experiment-run.ps1` 执行。

## 三、修订记录（改动即改动实验条件，必须在此留痕）

### 2026-10-05 · 冒烟轮后的唯一一处修订：A2 的输出契约显式化

**触发证据**：冒烟轮第一次运行 single 臂，`status=SUCCESS`、步数 76（是 multi 38 步的两倍）、
但采集到的回答**只有 448 字**，内容是一段收尾总结 —— 原文开头是
「✅ 深圳 → 惠州 3 日游方案已完成并交付（上方含 6 大部分…）」，
并列出了真实数据（88.5km/49.5km/70.8km/23.2km/126.7km、全程 359km、油费 228 元、预算 1986 元）。

**判断**：**这不是能力差异，是测量缺陷。** 单 Agent 把完整方案写在了中间轮次，
最后一条消息写成了"已完成 + 后续服务建议"；而我们采集的是**最后一条消息**。
multi 臂的最终消息恰好就是方案正文（3201 字）。照此对比质量，A2 会被系统性冤枉。

**修订**：在 A2 的 `SINGLE_SYS_PROMPT` 增加一段显式约束 ——

```text
★ 最后一条回复必须【就是方案正文本身】：
- 不要把方案写在中间轮次、末尾只写「已完成 / 上方已给出」之类的收尾总结；
- 不要在末尾附加「如需我再帮你生成 1 人版 / 导出表格」之类的后续服务建议；
- 用户拿到的就是最后这一条消息，它必须能独立阅读、内容完整。
```

**修订后实测**（重跑 single 臂）：回答 **3142 字**（multi 为 3201 字），长度可比，契约生效。

**为什么 A1 的提示词没有同步改动（如实披露这处不对称）**：
A1 的提示词**本来就有等价的最终输出契约** ——「最终输出使用 Markdown：包含①总体路线与时间安排
②每日行程 ③餐饮推荐 ④住宿建议 ⑤天气与注意事项 ⑥预算估算」，并且在冒烟轮里**确实合规**
（最终消息就是完整方案）。A2 的提示词有同样的句子但模型没有遵守，所以只是把同一条契约
写成可操作的禁止项。**这是输出形式的约束，不增加也不减少任何能力**；
若审稿人认为应当两臂同步加同一段，可把该段原样加到 A1 并重跑两条臂（约 104 万 token/对）。
