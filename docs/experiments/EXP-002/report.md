# EXP-002 上下文预算 —— 筛选轮结果

> **本文件是筛选轮（screening, n=1/档）的记录，不是最终结论。**
> 设计动机见 EXP-001 报告：单 Agent 每次 LLM 调用平均携带 19 万输入 token，九成以上是「只进不出」的工具结果。

日期：2026-10-05
范围：**机制 B（工具结果外置 + 按需取回）+ 机制 D（上下文计量）**
样本：single 臂 × P1 × **n=1/档**（令牌数已用 `-Recollect` 事后重采为权威值）

---

## 1. 结果

| 档 | token（权威） | 耗时 | LLM 调用 | 回答 | 盲评总分(/25) |
|---|---|---|---|---|---|
| **off**（基线） | **1,073,065** | 84s | 9 | 3917 字 | 22（action 4 / honest 4） |
| **on**（结果外置） | **200,209** | 106s | 11 | 3646 字 | **24**（action 5 / honest 5） |

**token 降低 81.3%**，质量**未下降（反而 +2）**，代价是**延迟 +26%**（84s → 106s）与 **LLM 调用 +2 次**（多出的调用是 `read_artifact` 取回）。

### 1.1 确认轮（2026-10-05 补测，treatment 补到 n=2）

单 Agent 方差极大，n=1 不足以当结论。本轮**只补 treatment 一档**（基线已有 3 个样本：EXP-002 的 off 档 + EXP-001 功能引入前的两次同题运行，二者等价）：

| 组 | 样本（P1 + single 臂） | token |
|---|---|---|
| **baseline** | EXP-001 r1 / EXP-001 r2 / EXP-002 off | 642,015 / 1,924,552 / 1,073,065 |
| **treatment** | EXP-002 on r1 / on r2 | **200,209 / 187,963** |

- treatment 均值 **194,086**；baseline 均值 **1,213,544** → **降低约 84%**
- **treatment 的最大值（200,209）比 baseline 的最小值（642,015）仍低 3.21 倍 —— 两组零重叠**

> **结论：这不是方差，是机制效果。** 幅度按 baseline 取哪个样本落在 **−69% ~ −90%** 之间；
> 保守表述建议用「**降低约 70% 以上**」，更稳的是引用"两组零重叠"这一事实而不是单一百分比。

> ⚠️ 仍未做的：treatment n=2 / baseline 的 EXP-001 两次运行早于功能引入（跨版本），
> 严格起见应再补 1 次 EXP-002 内的 off 档（约 100 万 token）。但这会显著加成本，且零重叠已足够支撑结论 —— **由使用者权衡**。

## 2. 机制证据：逐次调用的输入曲线

`[ContextMeter]` 每行给出一次 LLM 调用的精确输入 token（call# 是进程内全局计数，#1–#9 = 基线，#10–#20 = 外置开启）：

| call# | 输入 token | 说明 |
|---|---|---|
| 1–4 | 5,041 → 8,133 | 基线起步 |
| **5** | **167,976** | ★ 某次地图返回（约 16 万 token 的单条结果）进入上下文 |
| 6–9 | 214,213 → 219,860 | **之后每一次调用都要重发它** |
| — | **累计 1,061,165** | |
| 10–13 | 5,312 → 9,259 | 外置开启，起步相同 |
| 14–20 | 15,094 → **28,157** | 同类工具结果只留摘要，曲线被压住 |
| — | **累计 183,496** | |

> **结论：成本的主因不是"工具太多"，而是"单条巨大工具结果只进不出、之后每次调用都重发"。**
> 这也修正了我在 EXP-001 报告里的一个判断：当时说"九成以上是累积的工具结果"方向对，但**真正的形态是"少数几条超大结果长期驻留"**，不是均匀累积。

另注：同一次外置运行里，`[OffloadingMcpClient]` 共触发 **5 次**（map_weather 6978 / map_search_places 4646 / 7160 / 11406 / 13116 字符）。

## 3. 下一个瓶颈已经显现：工具 schema

`[ContextMeter]` 显示每次调用的固定开销约为 **schema 9,760 字符 / 25–28 个工具**，占首轮输入的 **≈78%**（首轮总输入 5,041 token）。

**含义**：结果外置解决的是"增量"，而 schema 是"底价"。把底价从 ~4k 压到 ~1k，是机制 A（工具 schema 按需挂载）的预期收益 —— **这是有数据支撑的下一步，不是猜的**。

## 4. 本次开发中踩到并修掉的 5 个坑（都已修，细节见 `DECISIONS.md`）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | 门禁 `--max-time 8` 对 SSE 端点太短 | 好地址被误判失效、整批被拦（**0 token 损失**） | 提到 20s + 重试一次 |
| 2 | **PowerShell 数组对 `-eq` 返回数组** | `ConvertTo-Json` 产出 `"contextBudget":[]` → 服务端 **HTTP 400**（不烧 token，极难发现） | `[string]@($x)[0]` + `[bool]` 显式转换 |
| 3 | 坑 2 写出的文件名含 `System.String[]` | **PS 把路径里的 `[]` 当通配符**，`Get-Content -Raw` 参数绑定失败 → 整个重采循环中断 | 读写一律用 `-LiteralPath`；解析失败只跳过 |
| 4 | 传输错误被静默吞掉 | 一轮变成"没有数据"，与"数据为 0"无法区分 | catch 里显式打印错误 |
| 5 | `ContextMeter` 用 `getTextContent()` | **看不见工具结果**（表现为"消息字符不涨、输入 token 涨 4 倍"） | 改为遍历全部 content block |

> 坑 1–4 都属于同一类：**"看起来正常的错误数据"比"明显的报错"危险得多。**

## 6. 机制 A 与机制 C（2026-10-05 追加实现并实测）

### 6.1 机制 A：工具按需挂载 —— ✅ 有效

**做法**：用一次极小的模型调用（无工具）判断该需求是否需要**真实地图数据**，不需要就不挂那 10 个地图工具。
分类失败/超时**一律按"需要"处理**（宁多挂不少挂：多挂只多花 token，少挂会让 Agent 拿不到真实数据，属正确性问题）。

| 指标 | 全量挂载 | 按需挂载（跳过地图组） |
|---|---|---|
| 工具个数 | 25–28 | **15** |
| schema 字符（估算） | 9,760 | **5,284** |
| **首轮输入 token** | **5,311** | **3,025（−43%）** |
| 路由自身成本 | — | **143 token**（输入 99 / 输出 44） |

- 非地图需求实测：`[ToolRouter] 工具路由：…→ 跳过地图工具组（原始回答「NO」）`，任务照常完成（13s / 1376 字 / SUCCESS）
- 地图需求（P1）实测：`→ 挂载地图工具组（原始回答「YES」）`，**判定正确**（P1 确实要算路）
- **配套改动（必须）**：未挂地图工具时，系统提示词追加一段"本次没有地图工具，请基于常识并**标注估算值**，不要尝试调用不存在的工具" ——
  工具没挂却仍要求查真实数据，模型只会浪费轮次并可能编造失败原因（即已知缺陷 D2 的形态）。

### 6.2 机制 C：历史压缩 —— ⚠️ 已实现，但**当前负载下不触发**，且前提被 B 覆盖

**做法**：装饰 `Model`，当消息总字符超阈值（默认 30,000）时，把**较早的 `TOOL` 角色消息**掐头去尾留中段标记；
保留最近 6 条不动；保留 `id/name/role/timestamp`，`metadata` 只保留 ≤200 字符的小字段（大字段是压缩对象，小字段多为工具调用配对信息）。

**安全性**：只改"发给模型的内容"，**不动 Agent 自己的 Memory**；只压 `TOOL` 角色，SYSTEM / USER / ASSISTANT 原样保留。

**实测结果**：

| 项 | 实测 |
|---|---|
| 是否触发 | **否** —— P1 全程消息总字符峰值仅 **8,530**，远低于 30,000 |
| 总 token | 174,108 输入 + 12,386 输出 = **约 186,494**（对比 B 单独时的 194,086，**基本持平**） |

**判断**：C 的前提是"历史文本膨胀"，而本项目里**膨胀的主因是单条超大工具结果** —— 那正是机制 B 已经治掉的。
在 B 生效后，历史里剩下的都是小消息，C 没有可压的东西。

> **因此 C 保留实现但不作为主线**：它是通用兜底（对非 MCP 的长文本历史仍然有效），但在本项目的实测负载下贡献接近 0。
> 这一条本身就是有价值的结论：**优化要针对实测到的膨胀形态，而不是"看起来应该会膨胀的地方"。**

### 6.3 一个尚未解释清的计量缺口（开放问题）

`[ContextMeter]` 在 P1 最后一轮报告：**输入 27,157 token**，但可计量的内容只有
「消息 7,527 字符 + schema 9,760 字符（估算）」—— 按最宽的比例估也只有约 1 万 token，**约 1.7 万 token 来源未解释**。

最可能的解释是**工具 schema 的真实 JSON 体积远大于 `Map.toString()` 的估算**（A 的收益 −43% 也指向同一方向）。
**确定的验证手段**（需要一次带采集的运行）：用 `tools/otlp-capture.ps1` 抓报文，直接量
`gen_ai.tool.definitions` 与 `gen_ai.input.messages` 的字节数 —— 二者在 span 里是明文 JSON。

> ⚠️ 在此之前，`[ContextMeter]` 里的**真实 token 数可信**（来自厂商 usage），但**"schema vs 历史"的占比只能当方向**。

### 6.4 一个流程陷阱（本轮踩到，已修）

**构建失败后仍用 `-SkipBuild` 启动 = 静默跑旧 jar。** 本轮一次编译错误导致 `BUILD FAILURE`，
但由于"构建"与"启动+运行"写在同一条命令里且没有校验，服务照常起来了，于是**那一次运行烧的是旧代码的数据**（作废）。

**纪律**：构建与运行**不要无校验地串在一条命令里**；必须显式判断输出里有 `BUILD SUCCESS` 才继续，否则中止。
（这与 AGENTS 硬约束 13 是同一类问题的两个面：脚本不会替你校验状态。）

### 6.5 把结果外置补到多 Agent 臂 —— 结论被改写（2026-10-05 追加）

**动机**：机制 B 原先只挂在 manager 的单 Agent 模式上，而**多 Agent 臂里唯一的 MCP 使用者是 `routeMaking_agent`** ——
它持有同样那 10 个地图工具，会拿到**完全相同的"单条巨物"**。补上它只需把同一份
`OffloadingMcpClient` + `ReadArtifactTool` 用到 `RouteMakingAgentConfiguration`
（Agent 是 prototype 作用域，`ArtifactStore` 天然按 A2A 会话隔离）。

**子 Agent 侧的病灶证据（本项目第一次拿到子 Agent 的上下文数据）**：

```
[RouteMakingAgent] 工具结果外置已开启（阈值 4000 字符）
[OffloadingMcpClient] 第 1 次外置：map_directions 原长  79,539 字符 → 摘要 991
                     第 3 次外置：map_directions 原长  68,635 字符
                     第 5 次外置：map_directions 原长 104,209 字符   ← 单条 10 万字符
（共 7 次外置，6 次是 map_directions；合计约 47 万字符）
```
没外置时，这 47 万字符会**驻留在路线 Agent 的上下文里、每次调用重发一遍** —— 这正是多 Agent 臂 409k 的来源。

**同题 P1 的最终同台对比（权威值，MCP 健康）**：

| 配置 | token | 耗时 |
|---|---|---|
| multi 无预算（EXP-001） | 409,253（n=2：401,962 / 416,544） | 53s（50 / 56） |
| **multi + 结果外置** | **136,788（n=2：150,181 / 123,396）** | **162s（117 / 208）** |
| single + B | 194,086（n=2：200,209 / 187,963） | 105s（106 / 104） |
| single + A+B+C | 186,494（n=1） | 67s（n=1） |

**token 排序**：`multi+预算 137k` ＜ `single+A+B+C 186k` ＜ `single+B 194k` ≪ `multi 无预算 409k`

> ### ★ 结论被改写：EXP-001 的"单 Agent 更贵"是**成本假象**
>
> 1. 在**没有上下文管理**时，单 Agent 因为"工具并集 + 巨物驻留"而贵 2.2~3.1 倍，看起来是"架构劣势"；
> 2. 把**两臂都装上上下文预算**后，**多 Agent 重新成为最省的**（137k，比单 Agent 低约 29%）——
>    因为它的**上下文隔离是真实优势**：每种子任务的重上下文只活在对应子 Agent 的进程里；
> 3. 所以正确结论不是"哪种架构更好"，而是：
>    **架构差异在缺乏上下文管理时会被成本假象掩盖；把两边都治好，才能看清各架构的真实成本。**
>
> 这也回过头解释了 EXP-001 里那条"质量打平"：两条臂的质量本来就相当，成本差异才是被误读的那一项。

**耗时仍未定论**：multi+预算 的两次是 117s 与 208s（差 1.8 倍），而 multi 无预算是 50/56s。
多出的时间**可能**来自 `read_artifact` 的额外往返（Agent 要主动取回细节），也可能只是运行间波动 —— **n=2 且跨度太大，不作为结论**。

**运行间差异的来源也已看清**：两次 multi 里，路线子 Agent 分别调用了 **6 次（68,768 token，7 次外置）** 与
**2 次（4,599 token，0 次外置）** —— 差异来自**主管派给它多少活**，而不是机制不稳定。
